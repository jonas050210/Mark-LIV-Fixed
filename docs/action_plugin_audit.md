## Scope and method

This is a static security, dependency, secret-boundary, and compatibility audit of the 20 files in `actions/` and the plugin files in `plugins/`.

The audit checked imports, `TOOL`/`PLUGIN` declarations, subprocess and shell calls, file and path operations, browser/GUI automation, network calls, model calls, scheduler integration, config access, and background hooks. No plugin was imported, enabled, started, or called as part of this audit. No API key, token, certificate, personal-memory file, or other secret value was read or copied into this report. No dependency was installed and no plugin configuration was changed.

`take`, `later`, `needs rewrite`, and `skip` are recommendations, not activation commands. A plugin must not be enabled solely because it is marked `take`.

### Recommendation meanings

| Recommendation | Meaning |
|---|---|
| `take` | Suitable for the current scope after normal tests and the existing privacy/user-facing guard are confirmed. |
| `later` | Potentially useful, but defer activation until a focused compatibility or privacy decision is made. |
| `needs rewrite` | Do not activate in the current form. The boundary, validation, confirmation flow, or execution model needs a targeted rewrite and tests. |
| `skip` | Do not treat this file as a runtime feature. It is a template, placeholder, or otherwise not part of the current product surface. |

## Executive summary

### Recommended for the current scope

- `actions/reminder.py`: bounded local scheduling with sanitized message text and least-privilege Windows task settings.
- `actions/system_monitor.py`: read-only metrics; no subprocess invocation in the monitoring path.
- `actions/weather_report.py`: read-only browser search with URL encoding and no local file/system mutation.
- `actions/web_search.py`: useful read-only search/fallback path, provided external results remain untrusted model input.
- `actions/background_monitor.py`: useful as an explicitly user-configured helper; it stores topics and performs daily DDG checks.
- `plugins/document_review.py`: pure result validation/rendering with no direct network, file, or secret access; legal-advice limitations must remain visible.

### Defer

`computer_settings`, `file_controller`, `flight_finder`, `proactive`, `screen_processor`, and `youtube_video` have bounded or mostly read-only use cases, but need explicit privacy/compatibility decisions and targeted tests before activation.

### Do not activate yet

`browser_control`, `code_helper`, `computer_control`, `desktop_control`, `dev_agent`, `file_processor`, `game_updater`, the current `open_app.py`, `send_message`, `chat_takeover`, and `telegram_remote` cross a real OS, browser, file, code-execution, messaging, or remote-control boundary without a sufficiently strong common confirmation and isolation model.

The current checkout still contains the old `actions/open_app.py` with `shell=True`. The safer change is in the still-open PR #5 (`65b7ad2`), not in `origin/main`; it should not be duplicated or assumed merged.

## Plugins

The runtime loader deliberately skips files whose names start with `_`; therefore `_template.py` and `__init__.py` are not discovered as runtime plugins. The loader does import every other `*.py` plugin during discovery before the enabled flag is checked. That is a runtime import behavior to keep in mind: “disabled” prevents tool declarations, `run()`, and `on_launch()`, but is not the same as “never imported.” In addition, `memory.config_manager.get_plugin_enabled()` currently defaults an absent setting to `True`. On a fresh configuration, every valid discovered plugin is therefore exposed to the Live tool declarations unless `plugins_enabled` is explicitly populated with `false`; this conflicts with the audit constraint that plugins must not be activated blindly.

## Findings that must remain visible before activation

1. **Plugin discovery and defaults are not inert.** `core.plugin_loader.discover_plugins()` imports every non-underscore Python plugin to validate it. Disabled plugins are not exposed to the model and do not run, but import-time code still executes. `get_plugin_enabled()` also defaults missing entries to `True`, so a fresh configuration exposes all valid plugins by default. A stricter design should default to opt-in for high-risk plugins and use a manifest/static metadata pass before importing optional plugins.
2. **Model output is an untrusted control input.** This applies especially to browser, computer, desktop, code, file, game, messaging, and remote-control paths. Web pages, documents, screenshots, transcripts, and Telegram messages can all carry prompt-injection text.
3. **Local confirmation is not consistent.** `computer_settings` protects only selected irreversible controls. File changes, external messages, browser forms, game installs/shutdowns, and generated-code execution need separate confirmation and/or a constrained capability mode.
4. **A “home directory” boundary is not a complete sandbox.** Resolve and re-check every derived path, account for symlinks and races, and reject archive entries that escape the destination.
5. **Secrets stay outside this report and outside Git.** Keep API keys, bot tokens, OAuth files, certificates, WhatsApp session data, long-term memory, and `.env` files out of commits and logs. The audit did not read their values.

## Local/OpenRouter path

The isolated provider client in `core/llm_client.py` now accepts `openrouter` as a distinct OpenAI-compatible provider. Its chat, text-only, warmup, model-list, and streaming requests use the normalized `/v1` endpoint path; OpenRouter credentials are read from the local configuration and sent only as a Bearer `Authorization` header. The generic `openai` aliases continue to cover local OpenAI-compatible servers without requiring an API key. No provider key was read during this audit, and no local configuration was created or changed.

`call_llm_text()` now follows the configured provider instead of always posting to Ollama's `/api/chat`. This repair is intentionally limited to the reusable local/provider client. The running assistant's primary path in `main.py` remains the existing Gemini Live audio/tool loop (`models/gemini-3.1-flash-live-preview`); it was not redirected to `core.llm_client`, because that would require a separate, agreed STT/TTS and audio-session design. Gemini API access in `main.py` and `core/gemini.py` is therefore deliberately unchanged.

## Suggested next gate

Keep all `needs rewrite` actions/plugins disabled and do not install optional plugin dependencies just to test them. The local/OpenRouter repair does not activate any action or plugin. The next implementation pass should define a small capability/confirmation policy, then add isolated tests for the specific boundary fixes rather than enabling the high-risk tools wholesale.
